# Dashboard Kit

The tokens and components the iQMS Document Control dashboard is built from, packaged so any other page can be built in the same design.

- **Reference page:** open `kit/index.html` (served at `/kit/`). Every component is shown live, in light and dark, next to the code that produced it.
- **In use:** the application's Dashboard (`#/overview`) is rendered entirely from this kit, so the kit and the product cannot drift apart.

## Files

| File | What it is |
|---|---|
| `kit.css` | Design tokens (light and dark) and every component style. Self-contained. |
| `kit.js` | `DK`: one function per component, each returning an HTML string. |
| `icons.js` | The icons the kit draws, as inline SVG. Generated by `scripts/kit-icons.cjs`. |
| `index.html`, `reference.js` | The reference page. Not needed to use the kit. |

No framework, no build step, no dependency on the application stylesheet. Every class starts with `dk-` and every token with `--dk-`.

## Use it on a new page

```html
<link rel="stylesheet" href="kit/kit.css">
<script src="kit/icons.js"></script>
<script src="kit/kit.js"></script>

<body class="dk-app">
  <div id="page"></div>
  <script>
    DK.theme.init();
    document.getElementById('page').innerHTML =
      DK.pageHeader({ title: 'Dashboard', sub: 'What needs attention today.' }) +
      DK.dash({
        kpis: [{ label: 'Technical Review', value: 3, note: 'Awaiting review', href: '#/tasks' }],
        body: DK.card({ title: 'My Work', span: 12, body: DK.empty({ title: 'Nothing assigned' }) })
      });
  </script>
</body>
```

Text options are escaped for you. Options documented as HTML (`body`, `actions`, `tools`, `cells`, `figure`) are inserted as they are: build them from other `DK` calls, or escape them with `DK.esc()`.

## Components

| Call | Use it for |
|---|---|
| `DK.pageHeader({ title, sub, actions })` | Title, one visible line of description, the page's actions |
| `DK.button({ label, icon, variant, size, href, attrs })` | Buttons and links. `variant: 'primary'` once per page |
| `DK.iconButton({ icon, label, badge })` | Icon-only buttons in the top bar |
| `DK.seg({ label, value, items })` | Tabs and quick filters. Fires `dk:change` |
| `DK.dash({ kpis, body })` | The page grid: a KPI row, then cards with a `span` |
| `DK.metric({ label, value, note, flag, href, feature })` | KPI card. One `feature` card per page |
| `DK.card({ title, count, info, link, body, flush, span })` | The container for everything below the KPI row |
| `DK.lead(value, text)` | Headline figure above a chart |
| `DK.columns({ label, unit, items })` | Column chart, one linked column per stage |
| `DK.strip({ label, value, tone, figure, href })` | A figure on a different scale, as a meter under a chart |
| `DK.gauge({ value, label, state, tone })` | One ratio as a half ring |
| `DK.factors([{ label, ok, of }])` | What a score is made of |
| `DK.list({ items, empty })` | Rows of things that need doing; each row is one link |
| `DK.workList({ items, empty })` | Assigned work: title, status cells, one action |
| `DK.activity({ items, empty })` | Who did what, and when |
| `DK.empty({ icon, title, text, action })` | Empty state |
| `DK.stage(key, label)` | Lifecycle stage: `draft`, `review`, `changes`, `approval`, `publish`, `published` |
| `DK.due({ label, state })` | Due date with its state: `overdue`, `soon`, `ok`, `none` |
| `DK.badge`, `DK.count`, `DK.info`, `DK.avatar`, `DK.avatars`, `DK.meter`, `DK.icon` | Small parts |
| `DK.shell`, `DK.sidebar`, `DK.topbar`, `DK.search` | The application frame |
| `DK.theme.init / set / toggle` | Light, dark or follow the device |

Each function's options are documented above it in `kit.js` and shown with examples on the reference page.

## Rules of the design

The look depends on these more than on any single component.

1. **One green action per page.** Only one button is `primary`.
2. **One feature card.** The dark card marks the most important number.
3. **Colour has a job.** The green ramp is progress through the lifecycle, amber means someone must act, red means overdue and nothing else.
4. **Never colour alone.** Every state also has a word or an icon.
5. **Numbers come from data.** A metric is calculated, links to the list behind it, and shows the same count that list shows.
6. **Operational, not decorative.** A card earns its place by answering a question.
7. **Flat and consistent.** Cards 12px with a hairline border, controls 8px. No gradients, glows or oversized headings.
8. **Explain behind ⓘ.** One visible sentence under the title; longer explanations go behind the info icon.

## Theming

Set `data-theme="light"` or `"dark"` on `<html>` (the kit also reads `data-color-mode`). `DK.theme.set('dark' | 'light' | 'system')` stores the choice per browser.

To re-brand, override the brand tokens after `kit.css`. The lifecycle ramp and the feature card are derived from them:

```css
:root {
  --dk-accent: #1F5FAD;
  --dk-accent-hover: #184C8C;
  --dk-accent-soft: #EAF1FB;
  --dk-sidebar-bg: #0F2D52;
}
```

## Inside the existing application

`index.html` loads `kit.css` after `app.css`. `assets/mini-v1.css` then connects the two token vocabularies:

- the prototype's names (`--bg`, `--surface`, `--border`, `--text-3`, radius, shadows) point at the kit's values, so every existing page uses the kit's tokens in both themes;
- the kit's brand tokens (`--dk-accent`, `--dk-sidebar-bg`) point at the organization's palette, which Settings → Branding sets at run time.

So a colour, radius or shadow is changed in `kit.css` and nowhere else.

`assets/mini-workspace.js` shows how a page feeds the kit from live data: it prepares the numbers from `Q.tasks()` and passes them to `DK`. Application behaviour is attached through `attrs`, for example `attrs: { 'data-action': 'connect-doc' }`.

## Adding an icon

Add its Lucide name to the list in `scripts/kit-icons.cjs` and run:

```bash
node scripts/kit-icons.cjs
```

The script reads `vendor/lucide.min.js` and fails if the name is not in that set.
